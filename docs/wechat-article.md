# 我给 Agent 做了一块 16×16 的屏幕

两帧像素图刚接起来，画面就闪个不停。原来亮着的点灭了，下一处又突然亮起。变化能看懂，眼睛却总被那一下闪动拽走。

这块屏幕最初只有 8×8 的设想。我想让 Agent 回答时，除了给文字，还能在浏览器里画一张很小的图。后来画布扩到 16×16，规则也定得很简单。四位十六进制数代表一整行像素，十六个数拼成一帧。给一帧，图就静静待着；连着给几帧，它便动起来。

刚开始，画面总带着一个圈。16×16 原本就只有 256 个位置，固定轮廓占去一圈，留给内容的地方很快不够了。这圈得删。页面上的说明和预设图案也撤掉，只留下像素画和回复文字。Agent 想画什么，由这次回答来决定。

程序里没有给“开心”准备现成的笑脸。Agent 得自己选择哪些格子亮、哪些格子灭。有时图形会画歪，读者需要猜一会儿；有时冒出一只事先没人画在模板里的东西。十六行数字写起来比点一个表情按钮麻烦，留给变化的空间也因此多了一点。

接下来要解决的是让它在每次回答时真的用上这块屏幕。我写了一个 Codex Skill，把像素格式和发布方法交给 Agent。它选择画面、写出每帧的数字，渲染器把数字点亮，并安排像素怎样走到下一帧。后来 Agent 画过跳舞的机器人，也画过一只摆动的水母。图形有时很直白，有时会绕一个弯才让人认出来。

画面开始从一帧过渡到下一帧时，渲染器的问题也暴露了。最初像素直接从旧位置奔向下一帧，试看的反馈很干脆，还是会闪。我把移动改成逐格进行，让一个像素每次只走一格，又去掉淡入淡出。速度先后调过几次，最后定在每格 20 毫秒。固定时间切帧容易打断还没走完的像素，于是程序改为等所有像素到位，再停 300 毫秒，下一帧才开始。后来四个机器人姿势循环起来，才有了跳舞的样子。

做这件事时，我也一直在想，Agent 画出的东西算不算情绪表达。我觉得算。它可以根据回答挑选形状和动作，读者也会从画面里读到好奇、雀跃或者迟疑。至于 Agent 有没有相应的主观感受，这块屏幕回答不了。它能做的事情很具体，让一段文字旁边多出一点可见的语气。

现在我把项目放到了 GitHub，采用 MIT 许可。它用浏览器页面展示画面，Python 脚本在本机发布回复，Skill 告诉 Agent 怎样使用。仓库里放的是程序和使用规则，运行时写下的回复数据被排除在版本控制之外。

展示链接目前只读取最新画面，重新打开旧链接也一样。历史回放还没做。这块小屏幕眼下更适合陪着一次正在进行的对话。
